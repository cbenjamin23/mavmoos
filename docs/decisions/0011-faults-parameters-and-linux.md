# 0011: Process faults, parameter service and clean Linux reproduction

Date: November 3, 2026. Status: accepted implementation scope; the detailed policies below are engineering choices under the user's authorization, not individually reviewed product requirements.

## Authorization and limits

The user authorized three concurrent streams: fault testing, the parameter plugin and a clean Linux build, with archived decisions/results, unchanged stock pHelmIvP and no real vehicle control. They also authorized continuing when the direction remains clear. This extends decision 0010's simulation work; receive-only remains the default and the exact owned native-simulator PID/socket guard remains mandatory for all effects. Nothing here authorizes a hardware backend or a physical flight.

## Choices and reasoning

1. **Keep protocol features independent of helm authority.** The parameter module consumes the shared FC context and proposes typed parameter operations through the host. Reads/listing need a fresh heartbeat, without home, position, EKF, flight state or navigation permission. Writes in this slice are limited to the simulator's `SIM_WIND_SPD`, REAL32, 0..20, with fresh disarmed/on-ground evidence checked again immediately before sending. This tests the common architecture with a useful non-navigation feature instead of duplicating a connection per module.
2. **Use parameter-protocol outcomes.** Queue admission, actual local send acceptance, PARAM_VALUE echo and explicit readback remain distinct. A write is not automatically retried. Its echo must be followed by a separate readback; a late accepted write may have applied even when its original operation times out. A list requires every concrete index, with bounded missing-index recovery under its original deadline. ArduPilot's unindexed change notifications are visible but cannot count toward completeness. A complete bounded JSON snapshot delivers the collected table through MOOSDB; it is not an atomic FC database transaction.
3. **Add a typed service and send callback, not raw packet access.** The runtime owns an independent queue of at most four parameter requests, dispatches at most one per iteration after control work, and repeats state/expiry checks after encoding. The new callback reports the local send return for that phase. This changes the development plugin ABI to version 2; host and modules must be rebuilt together. Existing plugin loading remains startup-only and trusted in-process code.
4. **Distinguish vehicle loss from loss of the MOOS producer channel.** A vehicle-only disconnect drops permission, cached navigation scalars and DRIVE evidence but retains the last observed all-stop state: an unchanged live stock helm does not repost that state periodically. New permission and fresh post-acquisition inputs are still necessary. A MOOSDB disconnect instead clears the all-stop state. Replacement of the database requires an explicit operator manual-override true/false cycle, observing source-qualified `ManualOverride` and then `clear`, followed by a separate acquire. MAVMOOS does not automatically perform this mission action. Earlier recovery failures remain archived.
5. **Move connection handling to the app owner.** MOOS communications callbacks publish atomic events rather than mutate runtime/module state concurrently with Iterate. The owner applies a current monotonic reset boundary, and the write path checks the disconnect epoch. This addresses a source-reviewed concurrency problem; no crash attributable to that race was reproduced. The check is not atomic with the syscall: a send already past the guard may cross disconnect detection, and accepted bytes cannot be recalled.
6. **Qualify Linux with source builds and executions.** Build pinned stock MOOS-IvP and the ordinary external altitude behavior in an owned Linux container at non-default paths, inspect ELF artifacts, verify original source hashes and execute tests there. Copying macOS libraries or compiling only the app is insufficient. No upstream edits, device mappings or externally published ports are used. Record package inventories because a pinned Ubuntu base does not freeze future apt repositories.

## Reference reuse

MAVROS supplies the feature/context/transport separation and parameter-specific list accounting, timers, missing-index requests and ArduPilot encoding quirks. Its ROS APIs and exact retry machinery are not copied. pArduBridge remains the UAV workflow reference; its named parameter reads for Precision Loiter illustrate useful non-helm access. Stock MOOS source determines event-driven all-stop and connection-callback semantics. Parameter references and fault source review identify exact revisions and locations.

## Alternatives and consequences

Keeping all-stop unknown after every vehicle interruption blocked legitimate recovery because stock helm suppresses an unchanged event. Retaining clear across database replacement would conceal the missing producer state. The selected distinction preserves strict database recovery while allowing explicit vehicle-link recovery.

A live per-value MOOS stream alone cannot deliver a complete table reliably because a key retains its latest value. The bounded snapshot adds memory and publication cost but gives the requesting client a complete indexed artifact. Longer/unbounded retries or silently renewing deadlines would conceal incomplete transfers; this slice reports incomplete instead. The supported bulk fixture uses AppTick 50 and RX128; full-table success at default RX32/AppTick30 is not claimed.

## Evidence and open work

See the batch record, fault results, parameter results and Linux reproduction. Each separates failures, fixes and exact passing configurations.

Independent review additionally reproduced acceptance of pre-reset queued/retained helm state with a fake host. Reset now installs a timestamp floor for DRIVE and, after MOOS loss, ALLSTOP. The floor is inclusive (`publication >= reset boundary`); scalar input remains strictly after acquisition. This is a local publication-time convention, not certified clock ordering. A separate mocked cleanup finding showed that seeding ownership from an already-reaped PID could select its unrelated replacement. Cleanup now polls before snapshotting and traverses descendants only for a still-live original child; exact private-mission reconciliation handles exited pAntler. Review and baseline/fixed reproductions distinguish these demonstrated component cases from native fault evidence.

Open: production request-history/session policy after 128 admitted parameter IDs; general parameter writes and other encodings; larger/slower parameter tables and ingress-age measurement; richer fault/load/packet-delay coverage; convenient operator UX for database resynchronization; additional transports, vehicles and hardware qualification. None is silently accepted by passing this simulation subset.
