# 0022: Local CI, firmware identity and capability evidence

November 4, 2026. Accepted implementation direction within the user-authorized CI/registry/firmware/Copter batch. Actual qualification is recorded separately in the batch ledger.

Keep one host and nine existing startup providers, development ABI 7. Firmware discovery is shared vehicle context, not a tenth feature plugin or an authority source. The host passively observes AUTOPILOT_VERSION and, only in explicitly enabled owned simulation control, may issue bounded standard REQUEST_MESSAGE reads. Receive-only and shadow still send zero MAVLink. Discovery, stream setup, parameters and missions share the existing fair protocol budget below control; discovery does not add a second protocol packet per tick.

Firmware observations retain target, session, original acquisition/read times, explicit unknowns, raw values and age basis. A stale advertisement remains labelled stale until session reset; publication never renews its sample. Wire version/capability bits and the short ArduPilot custom-version prefix cannot certify a full Git revision, capability behavior, readiness or authority. Active discovery has a fixed original ten-second window, at most three accepted attempts and bounded local rejection retries. Reset retires the old epoch. After a raw clock fault the host may begin a fresh read-only discovery epoch at a later valid owner clock and post-boundary heartbeat; it does not restore navigation permission. Stream setup retains its own numeric fault latch.

Separate three records: immutable firmware source profile; platform-specific native build identity/receipt; behavior qualification for exact capability/scenario/source/artifact inputs. Preserve the existing 4.7.0-dev snapshot as baseline and the official Copter-4.6.3 source as a candidate. A successful build or matching advertisement is not a passing flight. No moving tag or arbitrary executable/hash override replaces the exact owned native PID/profile/loopback route proof. Do not automatically promote a candidate or advertise a supported version range.

Use a single local CI entry point with explicit software, smoke and full tiers, fresh case outputs, copied CTest inventory, required-case and JUnit checks, original time limits and scoped cleanup. Full means the exact twenty existing native regression identities plus distance, two protocol benches and two broader Copter scenarios. Arbitrary `sitl` labels, substituted IDs or a summary-only PASS cannot replace them. Bind raw reports to the planned app/driver, native firmware and modules. Reverify source/profile/artifacts after the job. Keep Rover's independently configured identity separate from selected Copter firmware.

The capability registry owns definitions, interfaces, strategies, preconditions, outcomes, cancellation and test mappings. Historical qualification stays historical. Append new qualification reports only from retained exact raw result/archive evidence; do not rewrite registry definitions during a job. A held target being confirmed/cancelled differs from a one-shot operation completing. FC auto-disarm does not qualify an unexecuted explicit DISARM request.

Broader scenarios reuse ordinary existing stock-helm behaviors and the current Copter operation interface. Independently check FC observations, closed DataFlash state and application events. Require an early bound firmware observation in the new flights. Keep native execution serial under the existing common lock; software and source-build work may run independently. Process cleanup uses sampled matching PID/argv/group identities, not a security sandbox or an atomic kernel ownership handle.

Keep execution and code local. The user later explicitly approved creating and linking the private empty `cbenjamin23/mavmoos` repository; `origin` now points there, with no code/archive push or hosted activation. Manual future workflow definitions do not activate GitHub Actions or publish code. Source-built Linux qualification must report its actual tier and platform; macOS native results do not imply Linux native results. Stock pHelmIvP, physical transports and real vehicle control remain unchanged/excluded. Mission execution, general parameter writes and further Copter command families need their own contracts and evidence.

MAVROS supplies the shared context/plugin/discovery organization and software-CI precedent. Its inspected ROS-distribution CI and package release machinery do not establish a Copter release flight matrix for MAVMOOS. The [pinned comparison](../research/2026-11-04-copter-ci-compatibility/README.md) records the source basis. pArduBridge remains the primary UAV workflow reference; the new work makes that workflow's capability and version evidence more systematic.
