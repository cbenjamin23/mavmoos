# 0031 — Shared protocol plugins and a dedicated PX4 control provider

November 6, 2026. Accepted direction: vehicle commands and helm strategies belong in firmware-specific control providers. Prefer recognizable MAVROS feature boundaries for reusable protocol and observation plugins. The [v1 plugin tracker](../plugin-progress.md) defines a bounded denominator and distinguishes complete scopes, required software tests and native witnesses.

A single host retains the connection, accepted vehicle context and final handoff. Extend existing providers when an operator already looks there: fence save, replace and restore belong in `missions`, camera capture in `camera_status`, and gimbal point and release in `gimbal_status`. Data-family reuse does not carry firmware qualification. The Copter fence edit has a separate opt-in, typed storage and independent readback; it never enables a fence. The dedicated disarmed payload bench grants one original lease per selected component and shares one protocol slot with existing services. Camera ACK and new image evidence are separate. Gimbal ownership, observed pose and release readback are separate.

PX4 shares stock helm ingestion and common observations with the ArduPilot profiles. Its control provider owns different native mode and setpoint semantics. The host accepts an explicit acquire from airborne native Hold, requires post-acquire stock helm inputs before a bounded fixed-position prestream, sends one Offboard request, and waits for a newer Offboard heartbeat and new helm inputs before motion. A brief ordinary pause can keep a fixed local position under its original handoff deadline. Abnormal loss retires the setpoints and lets PX4 run its own configured Offboard loss action. No external native mode change silently restores permission. The host checks both active and intended Hold before starting a prestream, because PX4 can retain Offboard intention while it reports a failsafe Hold.

The initial PX4 effectful profile is limited to the exact local package executable path and owned UDP socket in the same Linux network namespace, with no usable interface other than loopback and no IPv4 routes. The pinned simulator binds its onboard port to a wildcard address; the namespace proof is mandatory for that socket. Existing ArduPilot direct loopback ownership checks stay unchanged. All control remains SITL-only. Real transports, general PX4 native actions, other PX4 frames, and stable-release support require separate scope and evidence.
