# Copter coverage, CI and firmware compatibility

November 4, 2026. **Status: research and proposed next implementation batch.** Current MAVMOOS baseline is `4c637002d5c6acc1c963e165b16200dda1fd9cd4`; qualified selected source remains `c1c38e93984189f290211edffd06ba9c05ac54a6`. This document adds no command, workflow, firmware upgrade or hosted service. Stock pHelmIvP and simulation-only effect boundaries remain unchanged. These recommendations are not an accepted release/support policy.

## Current coverage and gaps

The [Copter provider](../../plugins/arducopter_control.md) supports Guided, arm/disarm, takeoff, native Loiter hold, land, RTL and explicit Guided/helm goto/hold/return strategies. It consumes ordinary stock-helm course/speed/home-relative-height outputs. Mission storage transfer/progress and parameter services remain independent capabilities; storage transfer does not execute a mission. Facing policies exist, including per-request Guided-position choices; this is not every Copter flight-mode, setpoint, yaw/ROI or payload interface.

Latest qualification is 65 normal / 64 sanitizer / 64 clean Linux software CTests, 20 existing native regressions, a new 5/8/5 m stock-helm range flight and two new disarmed native protocol benches. Those totals include a Rover regression and focused service/fault tests. They do not mean 23 complete Copter mission types, exhaustive Copter command coverage, or equivalent qualification on every OS/firmware/frame. The current Linux 0.8 result is software-only; earlier native Linux layers are separate evidence.

The actual pinned ArduPilot source `04cf6486e8d42ce138de816e8466244346ed77cb` identifies itself in `ArduCopter/version.h` as **ArduCopter V4.7.0-dev**. Current results qualify that exact snapshot/configuration; there is no demonstrated stable-release support range. Generated MAVLink is separately pinned at `a2d0ecf011a4aaa7840480e43f4e38d8c9e79d29`. Wire-schema version, flight firmware version and MAVMOOS plugin ABI are different compatibility dimensions.

Live inspection found no tracked hosted-CI configuration, no Git remote, and no production `AUTOPILOT_VERSION`/firmware-capability handler. We have CTest, source-built Linux recipes, owned-native fixtures and rigorous archives; their execution has been locally orchestrated. Some new native cases require explicit frozen hashes and are invoked separately from the 20-case CTest graph. A CI entry point must include them deliberately. No hosted pipeline has been enabled by this research.

## What MAVROS supplies as precedent

MAVROS `ros2` resolved to the already-inspected commit `2d3f4db1101c7950c8817a9d788f0d11106fb261` during this review. The source manifest pins the selected files and the existing immutable archive.

- Its [command plugin](https://github.com/mavlink/mavros/blob/2d3f4db1101c7950c8817a9d788f0d11106fb261/mavros/src/plugins/command.cpp) provides generic COMMAND_LONG/COMMAND_INT services plus convenience actions. This exposes a broad wire interface; it is not a per-command promise of vehicle readiness, control ownership or observed completion.
- Its [system-status plugin](https://github.com/mavlink/mavros/blob/2d3f4db1101c7950c8817a9d788f0d11106fb261/mavros/src/plugins/sys_status.cpp) requests AUTOPILOT_VERSION, stores FC capabilities and software/custom versions, and handles an ArduPilot-specific custom-version representation. It has a default-capability fallback if discovery fails. We should reuse discovery/stack-specific organization while keeping unknown evidence explicit.
- Its [main CI](https://github.com/mavlink/mavros/blob/2d3f4db1101c7950c8817a9d788f0d11106fb261/.github/workflows/main.yml) runs industrial_ci across ROS distributions with transport end-to-end tests enabled; [coverage CI](https://github.com/mavlink/mavros/blob/2d3f4db1101c7950c8817a9d788f0d11106fb261/.github/workflows/coverage.yml) tests/reports coverage for libmavconn, core and extras. These files do not establish an ArduCopter release-by-release flight matrix. This is a finding about the inspected workflows, not a claim that no other integration testing exists.
- Its [test_mavros README](https://github.com/mavlink/mavros/blob/2d3f4db1101c7950c8817a9d788f0d11106fb261/test_mavros/README.md) explicitly labels the older SITL hand-tests historical. Current package test coverage and complete vehicle-workflow qualification should not be conflated.
- MAVROS releases its own ROS package versions independently of Copter firmware; the [ROS2 release repository](https://github.com/ros2-gbp/mavros-release/blob/ad4c89fd3b97a4fac4a058a75a0c3f5301d692ac/README.md) records Bloom releases into ROS distributions. A new Copter release does not imply one new fork of every plugin. Stable MAVLink interfaces, capability discovery, targeted stack/firmware adaptations and regression evidence are the relevant model to borrow.

## Proposed next batch

1. **Capability/coverage registry.** Enumerate meaningful Copter operations against official [Guided commands](https://ardupilot.org/dev/docs/copter-commands-in-guided-mode.html) and [ArduPilot interface families](https://ardupilot.org/dev/docs/mavlink-commands.html), then check exact supported firmware source. Record MOOS interface, owner, MAVLink operation, mode/prerequisites, ACK versus observed result, cancellation/handback behavior, implemented/deferred/unsupported status, test IDs and qualified firmware/profile cells. Group native/Guided/helm variants under the Copter control provider. Avoid treating a generic encoder as a completed operation contract.
2. **One CI entry point and hosted workflow definitions.** Reuse the existing build/test machinery. Per PR: software, loaded modules, fake clocks/I/O, original expiry/cancellation, stock-helm integration, shadow/RX_ONLY zero output, and a short native lifecycle. Nightly/release candidates: full native/fault/concurrency suite including the three separately qualified additions, longer missions, sanitizers and firmware/platform matrix. Assert required scenario IDs are registered and executed; missing SITL prerequisites must not silently produce complete-qualification status. Preserve original failing evidence and report skipped/unavailable jobs explicitly. Parallel CI jobs need isolated runners/containers; native cases within a runner retain the existing serial lock and ownership checks. Hosted activation requires a selected remote; none is created or published here.
3. **Versioned firmware manifests and discovery.** Centralize source commit/submodules, release label, frame, fixture parameters, native binary hash per platform, toolchain, MOOS/behavior and generated-MAVLink pins. Replace scattered fixture constants through this reviewed manifest, preserving exact owned native executable/PID/profile/loopback proof. Add shared bound-vehicle firmware/capability observation, with freshness/session/unknown semantics. Reported version/capability bits do not certify behavior. Full source commits and binary identities come from the build manifest, not an assumed complete Git hash in the wire's custom-version field.
4. **A broader native scenario library.** Add complete reusable missions: takeoff → route → hold/behavior handoff → return → land, native versus Guided versus helm holds, native denial/prearm and mode-loss cases, cancellation at each operation phase, changed home/reference/estimator conditions, boot/session recovery, wind/configuration variation, concurrent services and repeated-cycle/longer soaks. Existing tests cover parts of this; the missing work is systematic coverage and measurable acceptance per capability/firmware, not merely more nominal paths. Any new fault fixture must preserve production endpoint and authority checks. Current parsed-receipt omission is not proof of radio/network-delay behavior.

Then expand commands in coherent families. Native AUTO mission start/pause/resume/exit is a substantial missing Copter lifecycle and requires explicit storage/control ownership plus helm handback. Camera/gimbal/ROI, additional modes, home/origin changes and broader setpoint types should be ranked against intended MOOS workflows. Mission execution and general parameter writes remain excluded from the present implemented scope; this note does not authorize their implementation.

## Proposed upgrade and release policy

Maintain a blocking last-qualified baseline, add a stable Copter release for qualification, and optionally support a previous qualified stable release. Resolve latest stable/beta/main to immutable commits before building; moving upstream development builds run as advisory compatibility checks until promoted. Keep these roles visible rather than calling every observed version supported.

For an upgrade: create a candidate manifest, build a fresh native artifact, run the same required capability/mission/fault matrix, inspect changed modes/commands/parameters/telemetry, add narrow adapters if needed, and promote only passing capability/profile cells. Keep the prior baseline passing. Change firmware and generated MAVLink independently where possible so regressions remain attributable. A beta/main failure should produce an actionable compatibility report without silently replacing the blocking baseline. Retain unsupported/unknown outcomes rather than auto-retrying or assuming success.

Release tags should produce a matched host/plugin package, examples, version/ABI/dependency manifest and compatibility report from tested artifacts. High-volume raw CI logs belong in retained CI/release artifact storage; concise decisions, coverage indices and immutable evidence hashes belong in Git. Release qualification evidence needs durable retention. This is packaging/delivery to the development/SITL environment; real deployment/flashing remains outside scope.

Outstanding choices include remote hosting/visibility, supported firmware window, runner architectures, artifact storage/retention and which new command family follows the coverage audit. Primary recommendation: establish CI and compatibility tracking now while broadening existing Copter scenarios in parallel, before spending another large batch entirely on new plugins.
