# MAVMOOS whole-plugin build queue

November 6, 2026. Work through complete operator workflows, with isolated builders and independent review. Close the Rover qualification as its own source freeze while starting the next independent modules. This queue is a plan and a record of why the work is ordered this way; the dated qualification ledgers say what passed.

Keep one startup host, one selected vehicle-control provider, shared target identity and egress, stock MOOS-IvP, and owned loopback/SITL. No hardware routes, hosted pushes or uploads. Group closely related strategies with their owner. A passive sensor/diagnostics capability is complete when a configured operator can read the named observations, tell what they mean and how old they are, and reproduce what the simulator or generated source proved. Native support is per sender and fixture.

| Order | Whole plugin or complete expansion | Operator workflow and acceptance |
| --- | --- | --- |
| 1 | **ArduRover ground and boat** | Complete stock helm, native modes, direct navigation, hold, return, cancel and recovery on the pinned ground and differential boat cells. Independently witness active boat correction under current and unchanged helm. Already in qualification. |
| 2 | **Optical flow** | Read bounded per-sensor optical flow and quality. Keep raw and integrated families, frames, optional distance and producer timestamps separate. Verify generated delivery, source, trimming, invalid reports, stale/reset and zero output; use pinned simulated flow if it emits the supported family. Reference MAVROS `px4flow`. |
| 3 | **Terrain status** | Inspect reported position, available height, datum, and tile backlog without becoming a tile provider or changing NAV. Verify disabled/unavailable, geographic limits, stale/session and zero output. Reference MAVROS `terrain` and the actual AP_Terrain sender. |
| 4 | **Navigation monitor** | Compare FC-reported target and controller error as separate observations while diagnosing a mission. Decode local/global target masks and frames without confusing target commands, FC reports and estimated state. Require real app traces and one native controller-output witness when available. Reference MAVROS target and navigation output paths. |
| 5 | **Obstacle and proximity under distance_sensor** | See discrete ranges and angle-indexed obstacle bins with different validity. Preserve frame, angle offset, min/max and the no-obstacle/unknown distinction. Verify bounded output, trimmed extensions and bad angular geometry; no obstacle injection or avoidance commands. |
| 6 | **Link status** | Inspect link quality, noise, remote congestion and any supported cellular metrics. Bind to the intended producer and retain raw RSSI representation, unknowns and age. Verify cross-component input cannot be mistaken for an authorized FC report. Reference MAVROS `tdr_radio` and `cellular_status`. |
| 7 | **GNSS receiver diagnostics under system_status** | Read independently aged primary/secondary receiver status and RTK quality. Keep unknown satellite and accuracy sentinels, fix type, receiver and actual units visible. No correction forwarding or estimator substitution. |
| 8 | **Wheel observations under odometry** | Inspect per-wheel distance and advancing/reset state on a pinned ground producer. Keep wheel order and signed distance explicit. No fake global pose and no inference that encoder slip means motion. Reference MAVROS `wheel_odometry`. |
| 9 | **Vehicle clock diagnostics** | Show boot time, UTC and any observed round-trip records as separate facts. Expose restart, unknown clock type and uncertainty. No remote clock may extend a navigation deadline. Start read-only; add an active probe only with a bounded source/epoch experiment. Reference MAVROS `sys_time`. |
| 10 | **Camera observation** | Discover one explicitly selected camera component and observe reported identity, settings and capture status. Prove component isolation, status freshness and no trigger or media upload. Preserve vendor fields and distinguish acknowledgments from observed capture. |
| 11 | **Gimbal observation** | Observe one selected gimbal's device and manager status, orientation and rates with raw frames/flags. Qualify source and axis conventions, staleness and no active ownership. Commands follow only once that shared owner and frame policy are defined. |
| 12 | **MAVLink files** | On a nominated disarmed simulator, browse a bounded permitted root and get one complete file into private local staging. Require correct session/sequence/offset, bounded retries, cancellation, exact bytes and protocol reset/cleanup. No upload, deletion or rename. Reference MAVROS `ftp`. |
| 13 | **ArduPlane control** | Deliver one complete conventional fixed-wing workflow: explicit acquisition, stock helm course/height intent, validated airspeed handling, Guided route, airborne Loiter/RTL, takeover and loss. Use a pinned native Plane frame; retain lift/speed and turn bounds. Prove real path, mode and altitude evidence. Takeoff/landing support needs its own actually observed workflow before being advertised. |
| 14 | **Expanded air data** | Diagnose measured/demanded airspeed and sources using the existing provider, with explicit m/s/pressure/reference differences and producer coverage. Supply Plane profile observations without giving them control authority. |
| 15 | **Mission management workflow expansion** | Use typed inspection and verified readback to manage one additional plan family on an owned FC, with complete cancellation, rollback uncertainty and no execution side effect. Preserve the existing flight-plan proof boundary. |
| 16 | **PX4 observation qualification** | Own a pinned PX4 SITL and qualify common odometry, estimator/air-data and clock fields by actual raw sender. Group checks on one boot. Keep protocol-compatible observation support distinct from ArduPilot mode policies. |
| 17 | **PX4 control provider** | After the observation pin and loss contract, add one complete multicopter Offboard workflow with prestream/entry, local target, explicit authority, hold/return/takeover and observed loss behavior. Same stock helm and host boundaries, PX4-specific flight modes. |
| 18 | **External navigation observation and owned injection bench** | Keep source, frame, covariance and time explicit. Add a simulated estimator input only with an exact named producer, permitted path, no authority side effects, and independent FC acceptance and dropout proof. Keep it disabled outside its bench. |
| 19 | **Rover native mission execution** | Reuse independent mission storage proofs for a typed stock Rover AUTO use case after home/rally semantics and persistent handback are pinned. Qualify motion, pause/abort, pilot takeover and restart uncertainty together. |
| 20 | **Camera operations** | Make one owned simulated camera trigger/capture workflow complete inside the existing camera provider. Prove addressed control, cancellation and captured frame identity separately from command ACK. Preserve the passive observation-only default. |
| 21 | **Debug values** | Inspect bounded named and indexed diagnostic values with independently aged samples, original name and timestamp semantics, rate limits and no command or NAV path. Port the useful subscription and type mapping from MAVROS `debug_value`. |
| 22 | **Component metadata and discovery** | Identify metadata from a selected component, verify the bounded document against its declared version/checksum, parse a supported schema and expose provenance and stale state. Begin with an owned document and a fixed local transport; no arbitrary URI fetching. [Protocol](https://mavlink.io/en/services/component_metadata.html) |
| 23 | **Native mode catalog** | List the modes a selected firmware actually reports, show the current and intended mode separately, and handle list change and missing or reordered rows. Keep numeric fallback and mode ownership explicit. Do not use a catalog row to authorize control. [Standard modes](https://mavlink.io/en/services/standard_modes.html) |
| 24 | **FC event timeline** | Read a bounded firmware event sequence with event IDs, gaps, source restart, unknown metadata and exact decode provenance. Reconcile bounded replay only if the selected simulator supports it. Keep events separate from status text and authority. [Events protocol](https://mavlink.io/en/services/events.html) |
| 25 | **Power system diagnostics** | Extend `system_status` to match smart battery identity and generator reports to their source and retain separate measured power, remaining energy and unsupported fields. Compare the trace with current battery/board status without replacing either. [MAVLink power reports](https://mavlink.io/en/messages/common.html#SMART_BATTERY_INFO) |
| 26 | **Actuator observations** | Extend `rc_io` to show reported actuator output channels, valid masks and frames without confusing RC inputs, commanded PWM, output feedback and actual motion. Qualify matched sender configurations and cross-check with ESC observations. [Actuator output status](https://mavlink.io/en/messages/common.html#ACTUATOR_OUTPUT_STATUS) |
| 27 | **Water depth observations** | Expose signed and invalid depth fields, bottom distance and the source's position/time in a marine observation provider. Verify producer axes, datum and missing or stale depth with a named simulated producer. Keep it separate from chart depth and autonomous avoidance. [ArduPilot dialect](https://mavlink.io/en/messages/ardupilotmega.html#WATER_DEPTH) |
| 28 | **Gimbal operations** | Complete one simulator gimbal ownership and orientation workflow inside the existing gimbal provider. Prove ownership, frame transform, observed pose, cancel/takeover and independent status. No old command may outlive its grant. |
| 29 | **Remote ID observations** | Inspect a selected owned producer's identity/status and bounded location reports without relaying, broadcasting, inventing location or combining stale subrecords. Keep the observer optional and qualify generated versus native senders separately. [Open Drone ID](https://mavlink.io/en/services/opendroneid.html) |
| 30 | **ArduSub control** | Add a full named underwater operating workflow after a pinned simulator and a clear depth/reference contract. Qualify acquisition, helm course/speed/depth, intentional hold/surface or handback, pilot takeover and loss; keep profile mode and authority separate from Rover and Copter. |

Rows 2–4 can be built together with private files and focused tests. Rows 5–11 have independent core work; root owns any receiver identity, shared API, app/build and capability registry changes. Firmware build/preflight and Plane/PX4 source research can proceed alongside observation work. Rows needing a new egress lane or vehicle control grant use an explicit integrated design and a serial native slot. If a native sender or test resource is unavailable, preserve the partial evidence and move to another ready whole workflow.

The Rover ledger closes row 1 for both owned models. The observer ledger closes rows 2–11 at their individually recorded evidence layers. The files and diagnostics ledger records completed rows 12, 14 and 21 within their evidence scopes. The event, depth and power ledger closes rows 24, 25 and 27 within their recorded scopes. The Plane ledger closes row 13 for the pinned airborne conventional model. The [source preflight](arduplane-source-preflight.md) and [operating contract](arduplane-readiness.md) retain the planning history.

Keep three queues moving independently. The passive queue can work ahead with separate owner files and grouped generated checks. Read/write services share the bounded host lane and get one disarmed native proof per distinct effect path. Firmware control follows the same integration sequence but needs native physical evidence and a separately reviewed fallback before anyone calls it supported. Once a release is pinned, run only the impacted native cells during iteration, keep one fast lifecycle smoke test, then run the full relevant matrix for a release candidate. A new upstream release can be discovered immediately; each affected plugin becomes qualified only after its declared pin passes.

Use the pinned [MAVROS catalog and implementations](https://github.com/mavlink/mavros/blob/2d3f4db1101c7950c8817a9d788f0d11106fb261/docs/plugins/index.md), generated MAVLink definitions, and pinned autopilot sender source for each plugin. Archive a small crosswalk naming the paths, message conventions reused, source-specific ambiguities and local differences. For firmware control use pArduBridge and Jeremy's archived bridge and the actual firmware mode code. Reuse source only with its applicable notices and provenance.

For each item: define operator output and scope, build in isolation, check normal and sanitizer component paths, independently review source/edge cases, exercise the real app with its intended configuration, integrate the exact checks and docs, and archive raw results and teardown. Combine passive observers into a shared generated matrix and one native capture where the sender supports them. Keep unit/loopback fast, smoke one actual lifecycle, and full native scoped to a pinned release or a changed workflow. Report every result at the level actually tested.
