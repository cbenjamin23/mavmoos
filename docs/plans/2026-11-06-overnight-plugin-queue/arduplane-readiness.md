# Conventional Plane provider readiness

The next control provider is a complete **conventional fixed-wing SITL workflow**, separate from ArduCopter and ArduRover. Use one pinned conventional `plane` model. Establish an already airborne, trimmed test condition through an owned simulator fixture and demonstrate explicit acquisition, a stock helm route with bounded course and home-relative height, native Loiter, return, pilot takeover, link/producer loss, and fresh handback. The artifact must show independent position, speed, altitude and FC mode at each handoff. An ordinary takeoff or landing controller belongs in this provider once that exact fixed-wing procedure has been observed; no Copter actions are aliased to it.

## What the pinned source permits

The selected Copter 4.6.3 source revision `92b0cd788ec29406f26c6f9c31d5ceedbd1cc538` also identifies `ArduPlane V4.6.3` in `ArduPlane/version.h`. That is a source candidate for a separately built and attested Plane executable. The existing Copter artifact is no substitute for a Plane build. Use the standard `plane` model and pinned defaults; record the actual platform, options, executable, frame parameters and firmware identity.

[Plane's command handler at that pin](https://github.com/ArduPilot/ardupilot/blob/92b0cd788ec29406f26c6f9c31d5ceedbd1cc538/ArduPlane/GCS_Mavlink.cpp#L835-L1045) accepts `MAV_CMD_DO_REPOSITION` as a geographic Guided point and optional loiter radius. It does not use that handler's `param1` as a speed setting. Set mode explicitly and forbid its auto-mode-change bit for streamed/admitted navigation. The Guided slew commands for course, altitude and airspeed are compiled by default at this pin, but use separate handlers and retained state. Its speed handler accepts airspeed within FC parameters. Do not reinterpret an ordinary ground-speed request as an airspeed or treat independent command acknowledgments as one applied motion decision. [Plane Guided commands](https://ardupilot.org/dev/docs/plane-commands-in-guided-mode.html)

Start with a bounded lookahead position/height intent and a known, verified FC cruise and minimum airspeed policy. The stock speed field must have an explicit contract and a supported range; in the first pinned workflow a configured speed intent can select the qualified envelope without silently changing TECS setpoints. Consider airspeed changes as typed, independently acknowledged operations after telemetry/wind and acceptance are defined. The mode and observation predicate must require fresh real airspeed and adequate height for moving control, not zero speed or airframe-specific actuator overrides. Record actual airspeed and groundspeed separately.

## Loss and release are part of the workflow

A fixed wing cannot zero its velocity or hold a point. Native Loiter is a bounded orbit with a verified entry and turn radius. A new mode or handoff must cancel older queued position/slew work. Test loss of stock helm mail while the FC link remains healthy separately from one-way link loss and bridge exit. Plane's Guided target and slew state can remain active after the bridge stops sending; local packet expiry alone is not an FC watchdog.

Design the initial simulator fixture with a separate firmware-owned link-loss behavior, measured after the actual monitored GCS heartbeat stops. Establish whose heartbeat the FC watches and ensure other fixtures cannot keep it alive. [Plane GCS failsafe reference](https://ardupilot.org/plane/docs/apms-failsafe-function.html) describes the applicable mode and parameter dependencies; verify exact source and actual behavior for the selected build. For a healthy-link helm release, prove a deliberate ownership handback/orbit policy and a final stale-command race. A silent or invalid NAV input never restarts flight authority on its own.

Acceptance is one complete operator workflow with normal app and stock helm, a pinned executable and fixture, fresh navigation from both axes, an airborne orbit within declared bounds, observed return, pilot takeover and an independent link/producer-loss outcome. Start the provider once those controller inputs and loss behaviors have explicit source/test contracts. All work remains local and in SITL.
