# MAVMOOS capability and firmware roadmap

November 5, 2026. The next delivery wave has three complete operator workflows. A separate receive-only PX4 witness can progress in parallel. Ground Rover and conventional Plane then get their own bounded control milestones. This roadmap prioritizes capability families and gives each one a provider boundary and an acceptance gate.

## Starting point

The current inventory is fourteen standard providers. The control providers are `arducopter_control` and `ardurover_control`. The transaction providers are `missions` and `parameters`. The observers are `telemetry`, `system_status`, `attitude`, `rc_io`, `distance_sensor`, `imu`, `odometry`, `air_data`, `esc_status` and `landing_target`. The default composition is receive-only telemetry. Two standalone examples demonstrate external provider authoring. The Copter parity checkpoint passed both 111-case software gates and scoped native evidence. Parity checkpoint · [External authoring workflow](../../development/external-plugins.md)

The preceding software freeze `6e8959f` passed 109/109 cases normally and 109/109 under ASan/UBSan. Its recent observation additions include generated-wire app results. The prior full native freeze `119f723` passed 29 Copter 4.6.3 cases and one separately pinned ground Rover case, plus 103 software cases. Those results belong to those exact app, firmware, platform and fixture identities. `odometry` accepts ArduPilot and PX4 identities and has PX4-shaped app-loopback evidence. A native PX4 cell is pending. Software and app results · Full native checkpoint · PX4-shaped evidence

Use one plugin per recognizable capability. Keep common MAVLink decoding, frame conversion, bounded transactions and MOOS presentation in the shared capability. Put source identity, available messages, timestamp meaning, flags, capabilities and storage quirks in explicit firmware profiles or adapters. A common message ID gives a shared wire contract. Producer semantics and native delivery need their own evidence. Keep modes, target encoding, acquisition, takeover and loss policy in the vehicle-control provider. All providers use the same host-owned send, deadline, cancellation and connection gates. Keep stock `pHelmIvP` and qualify effects only in owned SITL. ## When to start more vehicle control

**Start profile design in parallel now.** A new observation profile can qualify as soon as it owns a pinned instance and the receive-only gates pass. Move fuller vehicle control into the next control tranche after the current parity checks and the active shared-host wave pass. That sequence gives Rover and Plane the proven mission, command and bulk scheduling boundaries. Sensor work can continue independently. Every profile needs a named use case, exact build, input envelope, FC and MOOS ownership state machine, and observed success and loss criteria before it enables an effect.

### Ground Rover expansion

`ardurover_control` already has a pinned ground-Rover scenario covering stock-helm motion, native Hold, pilot takeover, RTL and disarm. Its current return criterion uses home with a wiped rally inventory. Start the next Rover increment with an explicit 2D stock-helm route or direct Guided waypoint, a bounded hold and return sequence, independent route arrival and speed evidence, and a second mission that demonstrates loss and reacquisition. Prove behavior with missing input, manual takeover, reconnect, rejected requests and original expiry. Wire replies and state observations must agree before reporting completion. Preserve current ground behavior while adding one exact native case with ordinary stock helm. [Ground Rover profile](../../plugins/ardurover_control.md) · Native matrix

Go when the user selects the first operator workflow, typed mission inspection can identify any relevant rally data, and the release/hold/return policy specifies where the vehicle should stop. Stop promotion if the new adapter needs Copter altitude assumptions, if the destination is ambiguous, or if a late request reacquires after takeover. Report firmware-owned selection separately from observed stopping position.

### Marine Rover after ground evidence

Add an explicitly selected boat profile inside the Rover capability when the intended marine use is known. Pin a boat simulator frame, steering/thrust model, heading or travel-course behavior, speed and turn limits, home or rally semantics, and the definition of a safe stop under current or wind. Ground Hold and marine stationkeeping are different outcomes. Start with disarmed RX and shadow, then one owned native route, measured drift or position hold, pilot takeover, stale data and return. Keep it a separate firmware/profile cell even when the modules share code. Go only when the user chooses a concrete boat frame and loss behavior. Stop promotion if the simulator cannot prove the selected marine outcome. [ArduPilot boat configuration](https://ardupilot.org/rover/docs/boat-configuration.html) · [Pinned Rover loiter implementation](https://github.com/ArduPilot/ardupilot/blob/92b0cd788ec29406f26c6f9c31d5ceedbd1cc538/Rover/mode_loiter.cpp)

### Initial ArduPlane

Begin the fixed-wing work alongside ground Rover as a separate read-only and shadow profile. Select one conventional fixed-wing SITL model and pin the actual Plane build. Trace fresh mode, airspeed, groundspeed, heading, altitude and home. Verify the bounded mapping from stock helm course, speed and altitude before the profile may send.

The local pArduBridge `e34a62e` source supplies relevant Plane precedents. It reads fixed-wing airspeed limits and target cruise speed, uses Guided course-over-ground and altitude commands, and treats fixed-wing takeoff as a preloaded mission start. Its Plane SITL setup can clear and replace the mission at startup, and its Plane landing path requests AUTOLAND. Keep that source comparison separate from product policy. Any mission edit stays explicit and verified. Choose the actual takeoff and landing mechanisms from the selected firmware. The inspected ArduPilot source compile-gates its Guided slew `COMMAND_INT` handlers and bounds speed by the configured airspeed envelope. The inspected direct takeoff handler is in the QuadPlane path. pArduBridge source comparison · [Pinned Plane Guided slew handlers](https://github.com/ArduPilot/ardupilot/blob/92b0cd788ec29406f26c6f9c31d5ceedbd1cc538/ArduPlane/GCS_Mavlink.cpp#L908-L1043) · [Pinned Plane takeoff handler](https://github.com/ArduPilot/ardupilot/blob/92b0cd788ec29406f26c6f9c31d5ceedbd1cc538/ArduPlane/GCS_Mavlink.cpp#L1187-L1205)

The first effectful Plane case should start already airborne under an owned fixture. Give the provider one explicit Guided goto or bounded track change, then hand off to a verified native orbit or return mode. Test minimum airspeed, a finite climb and turn envelope, mode-change rejection, timeouts, pilot takeover, link/input loss and reset. The fallback must maintain the aircraft's sustained-flight envelope under the FC's native policy. Advance to operator arm, takeoff and landing only after the user selects a launch/landing procedure, the dedicated mode or verified mission is bound to it, and repeated tests show both activation and observed outcomes. Stop promotion if the selected build lacks the command path, track and speed evidence diverge, or the fallback fails to maintain the selected safe flight behavior. [Plane Guided mode](https://ardupilot.org/plane/docs/guided-mode.html) · [Plane automatic takeoff](https://ardupilot.org/plane/docs/automatic-takeoff.html)

### PX4 control after portable observations

A native `odometry` pass can establish the shared observer and peer profile on PX4. For control, select a PX4 airframe and exact version, then define a separate Offboard authority and setpoint cadence contract with qualified mode-entry, mode-exit, loss and stale-target tests. Start in shadow and use one owned simulator motion case after it passes. Offboard requires its own continuous proof-of-life policy and configured loss action. Progress only after those requirements are demonstrated without weakening the shared expiry boundary. [PX4 v1.17 Offboard behavior](https://docs.px4.io/v1.17/en/flight_modes/offboard)

## Test budget and user decisions

| Gate | Plan and evidence |
| --- | --- |
| Inner loop | Incremental private builds and exact-ID decoder, state-machine or fake-wire tests. Aim for a warm focused pass in 60 s. Reuse a real app peer for related observers and send faults through software fixtures. |
| Integrated software | One normal gate and one ASan/UBSan gate per source freeze, retaining every required case. The review target is 4 min 30 s warm per gate. The previous checkpoint measured about 270 s and 317 s of supervised CTest. Preserve any contention or teardown failures and rerun against original limits in an exclusive window. |
| Native witnesses | Give each native test one firmware-specific behavior to prove and record real wire and scoped teardown. Group compatible workflows in one boot where setup, state and evidence allow it. Keep smoke at the existing single native Copter lifecycle. |
| Promotion | Use the full pinned matrix at integration checkpoints or firmware promotion. Review projected same-host runtime above 50 minutes. Native scenarios serialize per verified execution domain. A separately leased Linux domain can overlap an independent host cell with isolation and resource proof. Split a single cell only when workers are equivalent and exact required IDs, artifacts, profile, receipts and cleanup merge without gaps. |

Collect separate compile, inventory, test, per-case and teardown times. Mark unmeasured timing unknown. Parallelize disjoint builders, peer faults and independent checking. Give the integrator sole control of shared wiring, source freeze and native leases. [Timing and isolation plan](../2026-11-05-fast-feedback-and-observer-expansion/README.md) · [Local CI runner](../../../scripts/ci/run.py)

The user decisions that can change the roadmap are the first richer ground Rover mission or a preference to bring forward a specific boat, the initial conventional Plane route and native fallback, and any future payload or external-estimator owner. Explicitly resolve emergency LAND/RTL precedence during AUTO uncertainty before broadening that policy. Broader mutations, component routes and real deployment each need their own scope and tests. The immediate three workflows and receive-only PX4 witness can proceed under the existing stock-helm and owned SITL boundaries.
