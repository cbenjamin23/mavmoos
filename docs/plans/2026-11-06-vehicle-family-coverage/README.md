# Vehicle family coverage

November 6, 2026. MAVMOOS aims to provide a MOOS-IvP integration path for each upstream PX4 and ArduPilot vehicle family. The v1 provider milestone and the vehicle coverage matrix answer different questions. The former tracks complete plugin workflows. This matrix tracks which vehicles can use those workflows and which still need a control profile or a firmware interface study. [Scope decision](../../decisions/0033-cross-firmware-vehicle-coverage.md) · [V1 provider tracker](../../plugin-progress.md)

## What the matrix counts

A profile covers a vehicle behavior contract. Record the firmware family and exact release, airframe or drive type, supported operations, setpoint units and frames, motion limits, authority transitions and fallback. Verify that the selected vehicle and configuration match the profile before granting control. Models and boards can share a profile when their relevant behavior is demonstrated to be equivalent. New releases enter the matrix as candidates and earn evidence on the applicable scenarios. [Firmware evidence rules](../../../config/firmware/README.md) · [Control coverage guide](../../development/control-qualification.md)

Record shared observation, native commands, firmware mission execution and continuous helm control separately. An observer can work on an airframe before a control profile exists. An autopilot can run its stored mission while offering a different interface for live steering. Keep the MOOS request and stock helm interfaces consistent where the underlying behavior matches. Give users explicit status for unsupported workflows and configuration mismatches.

## Additional profile work

Use the same end-to-end acceptance for a new frame as for a new firmware family. For a hybrid airframe, name the stable phases, transitions and allowed commands, then qualify the actual flight and expiry, loss and takeover at the phase boundaries. Track native mission capability and live helm coverage independently. The current QuadPlane native and PX4 standard VTOL cells provide the starting witnesses.

## CI for each profile

1. List every supported helm and native command variant and its allowed states in the capability registry. Exercise the actual loaded provider with deterministic input for successful operations, incompatible profile selection, competing commands, stale input and cancellation at the final send. Cover each declared authority transition, including manual takeover, normal handoff, release and explicit reacquisition after abnormal loss.
2. Boot a pinned owned simulator and stock helm. Verify actual motion and limits, native mode changes and command effects from independent FC observations. Exercise rejected mode entry, normal and expired all-stop, pilot takeover, link loss and restart where applicable. For VTOL, verify both phase changes and that work queued for the old phase cannot send after handoff. Keep commands, assertions and exact raw evidence together.
3. Run affected native cells with `focused-native` during development and include required cases in the release qualification matrix. Group related scenarios per simulator boot where their starting state and acceptance criteria permit it. Bind archived results to the exact app, profile, firmware, platform and fixture. Track local SITL and future field evidence separately. [Control CI guide](../../development/control-qualification.md) · [Local campaign](../../development/sitl-release.md)
