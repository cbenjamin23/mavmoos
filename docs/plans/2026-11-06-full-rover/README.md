# Ground and boat Rover workflows

Extend the existing `ardurover_control` provider with two explicit profiles. Qualify the ArduPilot `rover` Ackermann fixture and `motorboat-skid` differential-thrust fixture on the existing pinned Rover executable. The boat profile uses the surface-boat heartbeat identity and the normal ArduRover mode table. Use stock pHelmIvP with ordinary planar behaviors in both profiles.

Jeremy's archived bridge gives the reference for desired course and speed, original MOOS publication time, manual takeover and the N/E velocity packet. Keep the shared host's leases and deadlines. A release or stale helm input retires the grant. While the exact selected vehicle still has fresh armed Guided evidence, the host may send one bounded zero-velocity target. The autopilot's Guided timeout is independent. Explicit native Hold requests a stop. Explicit boat Loiter asks the flight controller to maintain a position. A stopped boat can drift under tide and Loiter has its own position and speed response.

The operator workflow includes legacy Guided, arm, Hold, RTL, disarm and stock helm acquisition/release. Add a versioned route, hold, return and cancel interface with a shared owner. A Guided route uses fresh position to stream bounded planar course/speed toward a fixed nearby goal. This lets the same host retire all waiting guidance when the original operation expires or the pilot takes over. Arm, Loiter and RTL use their own explicit native paths. Completion follows fresh observations after the command or route begins. Ground Hold and Guided zero speed have separate semantics from boat Loiter. Rover retains a forward travel-course model and speed envelopes of 3 m/s for ground and 2 m/s for the boat's bridge proposals. Native mode behavior follows the simulated FC configuration.

The native acceptance uses one grouped route/lifecycle per profile and the existing ground regression. It must show independent position, speed and mode evidence, actual stock-helm travel, explicit operator route/cancel/stop/return, a loss or takeover boundary and fresh reacquisition. Boat qualification includes disarmed receive-only and shadow, the boat identity, differential thrust, explicit Loiter within a declared position bound, and a known modest simulated tide. The pinned source and simulator parameters define the tested scope. The generated tests cover wrong type, stale input, reset, invalid requests, deadline expiry and absence of sends from receive-only and shadow. The native harness captures independent MAVLink, uses exact process and socket ownership, verifies dependencies and artifacts, and proves scoped cleanup. Publish results with exact source, binary, fixture and archive hashes.

Use the same pinned firmware source and generated MAVLink definitions in the two profile tests. The pure backend, operations, and fixture can proceed independently after agreement on the profile and request grammar. Root integrates the host configuration, checks the mixed mode boundary and runs native scenarios under the shared lock.
