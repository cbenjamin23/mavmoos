How we test

Continuous integration and delivery (CI/CD) is a repeatable process for checking changes and qualifying a version for release. We test in layers because a message that looks correct in isolation may still lead to the wrong vehicle behavior during a mission.

  1. Test decisions and failures in software. We can deliberately send stale guidance, drop a reply or replay a command after restart. These checks make it possible to reproduce a specific edge case and see whether the bridge rejects it, holds authority closed or avoids a duplicate send.
  2. Observe the vehicle in simulation. In software-in-the-loop (SITL), real autopilot firmware controls a simulated vehicle. We check the effect independently through the reported mode, movement or recorded state. For example, a stop can require measured low speed, and a landing can require touchdown and disarm.
  3. Combine real mission phases. Longer scenarios run the IvP Helm alongside native autopilot modes. They include route changes, takeover, loss of guidance and recovery. For example, the Copter survey pauses a native mission, revises the helm route, and checks that a repeated abort request does not send twice. That exposes problems during the handoff between systems.

Before qualifying a release, we run the required software checks, verify the Linux installation from a different directory, and repeat the simulator scenarios from one clean source commit.

How we qualify new firmware

We keep a known tested version and run the same scenarios against a new firmware candidate. Each run records the exact firmware and vehicle configuration. That matters because a mode, fallback or transition can behave differently on a new version or a different frame.

We review changed behavior before promoting a candidate to the tested set. We keep the previous result and preserve failures so we can trace a change back to the firmware, vehicle setup or bridge.
