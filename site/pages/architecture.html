Architecture

One MOOS app connects the IvP Helm and other MOOS apps to the flight controller. Plugins add capabilities. The bridge checks when each one may send.

One bridge owns the connection

The MOOS app, iMAVLink, reads from the selected vehicle and passes each message to the plugins that use it. Sharing one connection lets every plugin work from the same vehicle identity and state. It also gives the bridge one place to settle which request a reply belongs to.

Vehicle readings carry their source and age. For example, a position report can become old while the app is still connected. MAVMOOS keeps the sample’s age and publishes navigation coordinates only when it has a usable estimate and a known origin. That gives the helm a position it can interpret.

The bridge can replace a waiting guidance target when a newer one arrives. Just before sending, it checks that the target is still current and the helm still has permission.

The helm publishes its usual variables

A waypoint behavior helps the IvP Helm decide where to go. pHelmIvP publishes its usual outputs, such as DESIRED_HEADING and DESIRED_SPEED, to MOOSDB. MAVMOOS reads those variables and translates them into MAVLink targets for the flight controller. Use the pHelmIvP you already have and configure the mission to provide the inputs the selected vehicle plugin expects.

Who has control

The flight controller always steers and stabilizes the vehicle. When the operator enables helm control, MAVMOOS sends guidance once the controller is ready and the helm has a fresh target.

To hand control back, the operator requests a flight-controller mode. MAVMOOS stops sending helm guidance and checks that the controller switched modes.

Some vehicles can hold briefly and resume when guidance returns. After a longer gap, pilot takeover or a restart, the operator must enable helm control again. MAVMOOS first checks that any potentially active autopilot mission has stopped.

Group plugins by what they own

Enable at most one vehicle-control plugin when the app starts. It handles native modes and helm targets together. For example, selecting native Hold and following a helm route both affect who steers a Rover. One plugin owns that decision for the vehicle, and the bridge applies the same send checks across control plugins.

Some shared plugins publish vehicle readings for MOOS apps. For example, a navigation app can use the age of a position report to decide whether it is still useful. Other shared plugins handle requests such as reading a parameter, transferring a mission or downloading a log. A live parameter read returns the value from the controller or reports a failure if the request times out.

Mission, fence and rally plans share the missions plugin because they use the same transfer channel. That plugin can coordinate cancellation and verify what the controller stored. By contrast, attitude, imu and air_data have separate plugins because orientation estimates, raw motion sensor readings and air measurements arrive at different rates and can become stale independently.

External plugins load at startup and must match the app’s binary interface, the agreement that lets separately compiled code work with the host. The host keeps ownership of the connection and sending rules. Browse plugins · [[external_plugins]]

Test guidance in simulation

Much of our testing uses software-in-the-loop (SITL), where real autopilot firmware controls a simulated vehicle. MAVMOOS has a dedicated shadow mode for testing how it interprets a MOOS mission. It publishes the targets it would send so you can inspect them in MOOS while MAVLink output stays off.

Start in receive-only mode if you just want to check telemetry. For a full control test, MAVMOOS and the simulator exchange real MAVLink packets over UDP loopback, which keeps the traffic on the test computer.

What we took from MAVROS and pArduBridge

MAVROS showed how to separate the connection, vehicle state and feature plugins. Its command, mission and sensor handlers give us a reference for message direction, units, coordinate frames and acknowledgements. pArduBridge grounded the ArduCopter and ArduPlane operator workflows and how they fit ordinary MOOS missions.

When MAVROS changes, we trace the affected messages to the local plugins and tests, even when MAVMOOS groups features differently.

MAVROS capabilities outside our scope

  • Direct control · actuator_control, manual_control, setpoint_accel, setpoint_attitude, setpoint_trajectory. The helm supplies navigation goals and the flight controller handles stabilization. Virtual sticks, actuator commands and lower-level targets would add ways to steer that need their own takeover and fallback rules.
  • External position and velocity inputs · mocap_pose_estimate, vision_pose, vision_speed. MAVMOOS has tested one input that supplies position and motion estimates. A new camera or motion-capture input needs checks for coordinate frames, timing and accuracy, plus tests of what the autopilot does if the feed stops.
  • Obstacle and route inputs · obstacle_distance_3d, trajectory. A MOOS app would need to supply an obstacle map or a timed path. We would then need to verify that the chosen flight controller uses it correctly and handles stale data.
  • Traffic, terrain and landing · adsb, terrain, landing_target. MAVMOOS handles selected incoming messages. Sending traffic back requires a trusted source of aircraft tracks. Serving terrain tiles requires reliable elevation data. Precision landing needs a target detector and a tested response when the target disappears.
  • Simulator interfaces · hil, sim_state. The test fixtures already connect to the simulator and measure the vehicle’s response independently. Keeping those interfaces in the fixtures lets the bridge use the same flight-controller interface in every test.
  • Peripheral and host tools · cam_imu_sync, mag_calibration_status, play_tune, companion_process_status, onboard_computer_status. The current camera workflow captures images without synchronizing them to inertial readings. Calibration progress and tunes are separate operator workflows. Host diagnostics are already available in MOOS.
  • Raw packet forwarding · tunnel. MAVMOOS exposes specific operations it can check before sending. Arbitrary payloads would need separate rules for who can send, where packets can go and how much traffic is allowed.
